# Gateway metadata journal and continuity checks

Scope: P05, P06, P09, P15, P16 and P19; partial T01, T04, T18, T20, T22, T36 and T54 evidence. The journal, observer and WebSocket supervisor are implemented and exercised locally, including a native WebSocket client with a loopback peer. [Periodic case inspection](case-inspections.md) now has offline coverage. Real Discord validation, periodic member/role reconciliation and production composition remain open. Nothing in these checks connects to Discord or registers a command.

## Narrow event boundary

`apps/core/discord/gateway-projection.js` projects only identity, guild availability, role IDs, membership/timeout metadata and channel ancestry. Unknown dispatch bodies are not inspected by the projection. Nicknames, channel names/topics, message bodies, forms, attachments and ban reasons never enter this metadata projection. A separate [core-only conversation sink](case-conversations.md) can retain registered-case observations in the same cursor transaction. No AI path, connector or general event-handler registry exists. The default metadata composition uses Guilds and Guild Members intents (3). Explicit case capture adds Guild Messages and Message Content (33283); required privileged intent access must be verified for the test application. Changing capture mode forces a new Identify. Discord documents these [event groups and intent requirements](https://docs.discord.com/developers/events/gateway#gateway-intents).

READY is checked against the configured bot, application and guild. A current guild snapshot must contain the configured community and responder roles. Discovery/resume URLs must use the bounded Discord Gateway host pattern, WSS and no credentials, arbitrary path, query or fragment. The supervisor appends only the fixed v10/JSON parameters. Gateway dispatch is an internal core capability for the authenticated socket supervisor; it must never be exposed as an HTTP or component endpoint.

## Atomic event cursor and revocation

`apps/core/storage/gateway-journal.js` uses a database lease and fence for one owner per configured guild. Its mapping hash binds role ownership to the saved session. An active owner cannot be replaced; a stale owner cannot append or renew. A changed mapping cannot silently reuse the saved checkpoint. The supervisor renews the 30-second database lease every ten seconds. These are development bounds requiring staging/load verification.

Each projected dispatch commits its cursor, relevant revocation epochs, member shadow metadata, retained channel exclusions and necessary reconciliation intents in one transaction. A failed transaction advances none of them. Duplicate or older sequence numbers have no domain effect. Increasing sequence numbers are accepted; a skipped range now retains a capture-gap marker rather than claiming uninterrupted history. It resumes from the committed cursor, not an uncommitted callback's sequence.

Member removal or Whitelist-loss evidence invalidates prior eligibility. Muzzled/timeout changes invalidate pending access. Role/owner changes revoke retained staff authority so a lost-and-regained role cannot revive an old moderator grant. These are revocation hints, not fresh role observations: replay never overwrites the last REST snapshot or grants Crew, Whitelist or case access directly. Reconciliation workers fetch current Discord metadata and enforce the usual policy before any effect. Revocation epochs are monotonic validity markers, not a count of unique real-world incidents; REST and Gateway evidence may each conservatively invalidate work.

Member events enqueue Crew/Muzzled inspection, excluding bot accounts. Departure and relevant role/channel events request case inspection. A child channel observed under a permanently excluded case ancestor gains its own permanent exclusion, which survives subsequent move/delete events. A configured-role deletion blocks delivery; Whitelist-role deletion also invalidates known eligibility.

[Participant membership authority](case-participant-authority.md) has an independent presence epoch in the authority table. Removal, bot identities and lost continuity invalidate it; ordinary role/authority updates do not. Removal also revokes capability grants when the authority table knew an identity before the member journal did. The [explicit participant workflow](case-participants.md) now retains invitations and includes their cases in recipient-removal inspection. Even a first-seen removal schedules repair; the current binding is rechecked before audience writes and private delivery.

## Resume and loss of continuity

Discord's [resume contract](https://docs.discord.com/developers/events/gateway#resuming) provides a session ID and committed sequence for replay. The observer keeps delivery unavailable until queued replay has committed, RESUMED has arrived, the guild is available and heartbeat health is current. A replacement observer may preserve active Shuttle progress when that checkpoint is successfully resumed. S17 tests persistence of the checkpoint across an actual isolated PostgreSQL stop/start; it does not test a host reboot or a real Discord replay.

If a new Identify is necessary, or the guild becomes unavailable, old membership episodes and authority cannot be proven continuous. The journal conservatively advances eligibility, access and presence validity epochs for known members, retires current Shuttle sessions and retains their historical progress. Old work requires a fresh run after reconciliation. It does not invent an absence observation, remove current Whitelist or clear a restrictive mute intent. The presence epoch now marks a provable membership episode: both observed departure and an unprovable gap invalidate it. A bot restart that successfully resumes its committed session does not itself force this reset.

The in-process observer has a bounded queue of 64 pending events, including bounded transient core case handoffs, serializes commits and binds callbacks to an opaque connection handle. Disconnect, queue overflow, processing failure, stale connection callbacks, expired heartbeat health and lost ownership cannot turn delivery on. Errors expose stable codes, never the underlying payload or driver failure. On disconnect, the local health gate closes immediately; the durable pause commits separately after outstanding journal work drains. A database-only claim can overlap that interval, so workers must retain the shared in-memory gate and pre-write continuity check.

## Connection supervisor

`gateway-supervisor.js` accepts explicit core-only credentials, a narrow connector, the observer, a fixed-route discovery transport, clock/random/timer adapters and a synchronous operator/recovery predicate. Construction opens nothing. `start(owner)` returns a promise lasting until stop or failure; callers retain it and await `stop()` during shutdown. The supervisor exposes only stable phase/error/count metadata. A successful connection does not override the independent recovery or operator gates.

Hello schedules a jittered first heartbeat and subsequent interval heartbeats. ACKs must match an outstanding heartbeat; missed/late ACKs invalidate health. Server heartbeat requests are answered immediately. Heartbeats use the received sequence, while Resume uses the last committed cursor after pending journal work drains. Reconnect uses the saved resume URL. Invalid sessions and session-expiry codes force fresh Identify when necessary; credential/intent/sharding failures halt. Backoff grows to 60 seconds plus jitter, and ten failures without a sustained healthy connection halt the loop. See Discord's [connection lifecycle](https://docs.discord.com/developers/events/gateway) and [close codes](https://docs.discord.com/developers/topics/opcodes-and-status-codes#gateway).

Every new Identify obtains current session-limit metadata through fixed `GET /gateway/bot`; a depleted remote allowance waits for reset. Migration 007 additionally limits this single configured application to 20 local reservations per 24-hour window. Reservations are serialized, retained across owner/database restarts and never refunded after an uncertain send. They are spaced six seconds apart, and sending must occur within one second of reserving, preserving at least five seconds between actual Identifies. The local ceiling is a conservative development choice, not Discord's published quota; it assumes this is the application's only Gateway deployment. Separate bots keep separate tokens. Resume does not consume an Identify reservation.

Only Identify, Resume and Heartbeat can be sent. Outgoing payloads are capped at 4 KiB, buffered output at 16 KiB, and sends at 110 per rolling minute. Incoming application parsing accepts uncompressed text JSON up to 1 MiB and only supported opcodes; malformed, oversized or binary input halts safely. No raw frame is logged or journalled. The Node built-in WebSocket assembles data before application code receives it: this parsing bound is **not** a bound on native frame allocation. Native memory behaviour, TLS/network failure and closing-handshake behaviour require staging/resource checks before release. No new WebSocket dependency was added.

Shutdown stops timers, closes admission, requests a resumable close (3000), and awaits owned authentication, journal and renewal work. Late events cannot affect the replacement connection. An intentional stop wins over an earlier disconnect still waiting on storage. The lease expires naturally after renewal stops; there is no force-takeover or budget-reset route.

## A healthy flag is insufficient

REST role reads, actor authorization, prepared role writes and case observations now require a continuity stamp. The stamp contains the durable owner/fence/epoch/cursor and a local ingress revision. A dispatch can make a connection unhealthy and healthy again during an awaited operation; its changed version still invalidates the result. This closes the earlier boolean-gate race.

The observer reports no current stamp while work is pending, replay is incomplete, heartbeat health has expired or storage ownership is invalid. Commands and dispatchers must share this observer and retain their separate activation/recovery checks. Outbox claims and pre-write checks additionally consult the durable Gateway state when a journal exists. Legacy synthetic fixtures with no journal explicitly inject a stable fake stamp; absence of a journal is not permission to deploy that fixture or bypass the required production observer.

A stamp, transaction and Discord request still cannot form one atomic operation. An already in-flight external effect can arrive after revocation and needs compensation. The journal is also not an independent recovery watermark: replaying Discord cannot recover missing internal withdrawals, retention/deletion decisions or other control records from an old database backup. T58 and production restore activation remain unresolved.

## Evidence and rollback

Six observer/projection contract tests and twelve supervisor tests cover identity/URL binding, role-map checks, ignored bodies, stale REST/prepared-case observations, connection handles, heartbeat expiry, ordered bounded work, overload, wire payloads, budget waits, fatal closes, reconnect limits, uncommitted cursors and shutdown races. G01–G15 use actual PostgreSQL with synthetic dispatch callbacks and simulated Discord HTTP. G16 tests concurrent reservations, the retained Identify ceiling, expired fences and window renewal. G17 uses Node's native WebSocket against a loopback-only peer, actual journal transactions and simulated REST role delivery: Identify, heartbeat ACK, Crew grant, reconnect, replayed Whitelist loss and Resume all run through the socket. S17 checks checkpoint and budget persistence across a real isolated database restart. CC24 separately exercises case-content intents and create/edit/delete observations over the native loopback socket; S37 retains content, gaps and cursor across two restarts. None is live Discord acceptance.

Migration `006-gateway-journal.sql` added lifecycle/checkpoint and member-shadow tables. Migration `007-gateway-identify-budget.sql` adds retained budget columns without changing earlier migrations. The session ID/resume URL remain in core storage; no bot token is stored there. The synthetic core identity receives SELECT/INSERT/UPDATE; knowledge has no core access. No dependency or permission grant changed.

Rollback must stop observers and delivery while retaining checkpoint, epochs and queued intent. Do not restart older role/authorization code that lacks continuity checks against an active journal, delete the journal to bypass a gate or lower epochs to recover progress. Only new synthetic clusters were migrated and stopped. Live permissions, connection compatibility, operational retry/cutover, Windows identities and independent recovery still need their release evidence.
