# Discord role delivery and recovery

Scope: P09, P15 and P16, with T18/T20/T21 recovery and ownership checks. This slice implements the core REST/role boundary and Whitelist grant/compensation dispatcher. The subsequent Crew/Muzzled dispatcher and signed moderation command path are documented in `docs/command-authorization.md`. No live Discord call, bot-token lookup, command registration, gateway connection or production activation occurs. There are no new package dependencies.

## Components and trust

`apps/core/discord/transport.js` has only fixed Discord API v10 routes for bot identity, guild roles/members, individual role changes, [case channel provisioning](case-delivery.md) and the bot's own [Shuttle screens](shuttle-screens.md). Core injects the token, fetch implementation, clock and an activation predicate. There is no default network transport, ambient token lookup, arbitrary URL, channel-history scan, attachment or AI interface. The screen adapter may fetch one retained own-message ID and projects its expected static body and control metadata within core. Response bodies are bounded to 512 KiB and errors retain only stable codes and retry durations. Redirects fail, and a five-second request timeout bounds the real fetch implementation. Before preparing a mutation, the adapter verifies that the token belongs to the configured bot through Discord's current-user endpoint.

`apps/core/discord/roles.js` reduces responses to role metadata. Observations are dated at request start so a slow response cannot become a fresh observation simply because it just arrived. They now require an unchanged [continuity stamp](gateway-continuity.md) across the read; prepared writes recheck it. Only an explicit Discord unknown-member response represents absence; missing access, an unknown guild, malformed data and an outage fail closed. Fresh observations alone cannot prove that no role change happened during an offline interval.

The role mapping uses verified IDs for Crew, Muzzled, Whitelist, Staff, lead ops and the bot, plus an explicit list of externally owned roles. `modules/membership/discord-policy.js` rejects overlaps, @everyone, managed/deleted roles, missing Manage Roles, timed-out bot contexts and insufficient hierarchy. Equal role positions fail closed as a development constraint pending staging verification. A projected context is frozen, tied to its adapter instance, expires after the existing five-second freshness bound and can be used for only one attempted change.

The transport writes through Discord's individual role endpoints; it never replaces a member's role array. This preserves roles owned by the Discord/BYOND integration. The hierarchy check follows the [Discord permission hierarchy](https://docs.discord.com/developers/topics/permissions#permission-hierarchy), and successful role writes require the documented 204 response from the [guild role endpoints](https://docs.discord.com/developers/resources/guild#add-guild-member-role). A successful response still does not establish application completion.

## Dispatch and late results

The dispatcher runs one bounded job per call and claims only `whitelist.grant` and `whitelist.reconcile`. It never consumes a case-provisioning or Crew/Muzzled reconciliation job. A caller-controlled component ID or old role snapshot cannot authorise delivery: the dispatcher fetches current metadata, reloads the member/session/definition under the store's locks, checks activation and the database delivery barrier, checks its lease, and only then attempts the role change. It fetches membership again afterward. The store confirms the role or commits cancellation and a compensation intent.

If a worker loses its lease or cannot determine an attempted write's outcome, it may record a new inspection intent, but cannot acknowledge the old job. Compensation checks current entitlement before removing Whitelist. A newer currently valid completion or fully read, eligible pending qualification is preserved; a missing role is never restored from an old completion. Removing a stale grant is itself an observed Whitelist loss, so a fresh Shuttle run is subsequently required.

An initial compensation can finish before a very late Discord write arrives. To handle that, `recordObservation` detects a newly present Whitelist associated with a cancelled/parked attempted grant and durably queues another inspection. The Gateway observer now feeds current observations into this operation, and its socket path has loopback coverage. Live composition and periodic reconciliation remain open; late-role compensation itself is tested through simulated HTTP and observations. No finite timeout or database fence can guarantee that an already in-flight Discord request will never finish later.

There is no transaction held across Discord. A concurrent policy change can still occur between the final check and a request; post-response reconciliation limits that window without claiming exactly-once effects. A role mapping change or cutover must reconcile queued work and verify ownership before delivery is re-enabled.

## Rate limits and blocked delivery

The transport honours server-provided `Retry-After`/`retry_after` and exhausted-route reset headers, as described in [Discord's rate-limit contract](https://docs.discord.com/developers/topics/rate-limits). It serialises requests by rejecting overlapping calls with a retryable busy result rather than retaining unbounded work. It does not immediately retry failed HTTP operations internally. A single core composition should share this narrow transport among its workers.

Queue retries persist a delay at least as long as the server requested. As a conservative single-bot policy, the database delivery barrier pauses all outbox claims for that delay, even for a route-specific limit. Workers recheck the barrier before mutating Discord. The pause survives a new worker/client and a database stop/start. Already in-flight requests cannot be recalled.

Unreadable or unsupported rate-limit durations halt that transport and persist an operator-review pause. They are never guessed shorter. Invalid credentials, missing permissions and hierarchy/configuration failures park the affected job. The parked intent, dispatch marker and epoch state remain retained. [Staff delivery review](shuttle-delivery-issues.md) provides a bounded, audited recheck for parked jobs tied to an actual Shuttle grant. It preserves possible effects and routes work through current-policy inspection; it cannot resume a global pause or override eligibility. This rate-limit barrier is not an independent restore watermark and does not pass T58.

## Validation and release limits

The added contract tests exercise fixed endpoints, individual role changes, ownership/hierarchy, malformed/absent/stale observations, bounded responses, redacted errors, cooldowns and disabled activation. D01–D14 use real isolated PostgreSQL transactions and an in-process Discord HTTP simulation. They cover normal grant confirmation, mute races, lease loss, lost responses, late arrival after compensation, preservation of a newer grant, unsupported job exclusion, durable Retry-After and pauses committed before or after a claim. S17 additionally verifies that a persisted delivery pause survives the test database stop/start.

No live Discord compatibility, channel-overwrite effectiveness or permissions staging is claimed. Signed mute/unmute, persistent actor authority, Crew/Muzzled delivery, private cases, Gateway lifecycle and Shuttle screens/controls have local evidence. The [OAuth authentication backend](dashboard-auth.md) now has synthetic and loopback coverage. [Ordinary intake](case-intake.md), [answer delivery](case-intake-delivery.md) and [Staff recovery](case-delivery-issues.md) also have synthetic evidence. Live composition/OAuth, final forms, remaining dashboard routes and unidentified results remain open. Bound Shuttle cases support [audited duplicate-channel selection](shuttle-channel-selection.md) with fresh seal verification. The source Shuttle presentation remains a draft. Production preflight remains disabled pending those adapters, verified guild/role IDs, Windows identities/ACLs, runtime distribution review and independent recovery evidence.

Migration `002-discord-backoff.sql` adds the singleton delivery barrier and reconciliation indexes; `001-core.sql` is unchanged. The core principal needs SELECT/UPDATE on the new barrier table, and migration privileges remain separate. The synthetic harness grants its isolated core principal the necessary table permissions. Production grants/provisioning have not been run.

Rollback: stop delivery, revert the adapter source if necessary and preserve the schema and queued state. Do not automatically drop the barrier table, delete parked jobs or replay old work. On this host only new synthetic clusters were migrated, exercised and stopped. Existing game/wiki services and Discord state were untouched.
