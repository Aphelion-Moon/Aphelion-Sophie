# Onboarding editor and fixed dashboard presentation

Scope: P05/P08/P13/P36/P37; R03/R04/R07/R16/R18; partial T03–T05/T19/T22/T36/T42/T43/T49–T51. This slice supplies a browser editor for authored Shuttle guidance. It does not read onboarding sessions, cases, conversations, files or transcripts. No model or external preview service is involved. No dependency, migration, production service or credential was added.

## Composition and access

`createDashboardPresentation()` preloads the fixed dashboard shells, stylesheet, same-origin JavaScript modules and manifest-selected avatar. Community, Casework and Configuration group the service navigation. The [ticket-form editor](dashboard-forms.md) shares the transport, workflow controller, shell lifecycle and static presentation while preserving separate domain rules. Inject it as `presentation` into `createDashboardAuthHttpServer`, alongside the existing `authoring` service. Both dependencies remain optional and absent by default; this factory does not open a listener automatically. Core remains the only Discord-token owner. The browser receives a Secure/HttpOnly session cookie and an in-memory CSRF proof, never the bot token or OAuth client secret.

The public shell contains only static UI and identity text. Its exact asset map never interprets a request as a filesystem path; query variants, traversal paths and unlisted files do not resolve. Assets require the configured Host and an empty GET request. They can load concurrently without occupying the single authenticated-operation slot. A shell being available does not mean authentication or publication is enabled.

The HTML uses external same-origin ESM/CSS and a restrictive CSP, with no inline script, style attributes, eval, third-party font, telemetry, remote image, arbitrary URL fetch or CORS exception. Responses are no-store, nosniff and no-referrer, and disallow camera, microphone and geolocation. Authored copy becomes text nodes; HTML-looking text is never evaluated or link-fetched. The local Markdown renderer uses safe DOM elements for static authored copy, without HTML injection, image fetching or mention resolution. Explicit screen boundaries match the publication; older copy retains its legacy pagination. This is not pixel-exact Discord rendering or a preview of a live member session.

`GET /auth/session` now includes `canEditOnboarding` (with `canEditShuttle` as a compatibility alias), resolved from current `shuttle.publish` authority when authoring is composed. This controls the visible workspace only. Every API operation independently authenticates, authorizes and checks CSRF where applicable through the existing services. Sign-in is not editing permission. The UI coalesces focus/visibility checks to at most once per minute while visible; back/forward restoration forces a check. Authoring rechecks do not set busy or disable fields. Transient connection failures preserve edits; actual permission denial clears them. A failed current capability check or sign-out clears loaded documents, comparison dialogs, history and pending requests from the controller and DOM. Previously displayed copy cannot be made unseen, and this is not an OS-level privacy boundary.

## Editing and recovery

The editor starts with five pages and supports 1–20 steps. Add a step after the selected one, move it earlier/later, or explicitly confirm its removal from the draft. Stable identifiers travel with their text; saved versions and active runs are unaffected. The last remaining step cannot be removed. Each step supports 1–5 explicit screens with add/reorder/confirmed removal and a local Markdown preview. Next/Back navigation precedes acknowledgement on the final screen. Older copy converts only when its screen text or arrangement is edited. Step title/screen editing is separate from the all-steps help-pause setting. Save creates a retained revision. Unsaved text remains only in memory, with no autosave or local-storage draft cache. Review requires a saved, unchanged revision. It shows current versus proposed copy/order, the help rule, screen text segments and the effect on new versus already-running journeys. Publication requires a review checkbox and a separate action button. A recorded publication does not claim Discord delivery or member access.

History uses the server's ten-record cursor pages. Inspecting a row is read-only. Using retained copy prepares a new unsaved document and never replaces retained history. Current unsaved edits must be saved or explicitly replaced through comparison before using historical copy or withdrawing a version.

Withdrawal has a separate review and checkbox. It shows current aggregate run counts, the older version selected for new runs or the absence of any remaining publication, and the block on unfinished pinned runs/pending grants. Earned Whitelist access and retained records remain. The confirmation reports the recorded action and possible pending cleanup; it does not claim that queued Discord edits have completed. Counts describe runs, not distinct members, and can change before commit.

A conflicting save preserves the local document. Reload opens an explicit comparison with the latest saved copy. The operator chooses which document to keep; there is no silent merge. Keeping the local copy prepares it against the latest expected revision, then requires another save. The complete copy is compared, including the help rule.

An uncertain mutation preserves its exact request ID and body, locks competing edits/actions, closes the dialog and exposes **Retry same request**. Every acknowledged action or receipt retry is followed by fresh reads. The UI does not infer present publication status from an old action receipt. An acknowledged action followed by a failed refresh is labelled as recorded with a separate reload failure, rather than inviting a second mutation. Permission loss can prevent delivery of a result after commit; the existing audit remains authoritative. Closing the tab can lose an in-memory uncertain request, so the browser warns before leaving with unsaved or uncertain work.

The transport uses only fixed same-origin routes, credentials restricted to the same origin, no-store fetches, rejected redirects and a 12-second client deadline. Logout is an empty POST with Origin/CSRF enforcement; a rejected logout is not described as a successful revocation. Provider/server response text and credentials are not logged or displayed.

## Presentation and accessibility review

The live identity text is Sophie / Community Services. The selected avatar is served byte-for-byte from `Sophie-Visual-Assets-v1` after its byte count and SHA-256 match the manifest. It has decorative empty alt text beside the live name, a contained rounded-square placement and a text fallback on image failure. No source PNG or planning-pack file was modified. This is the full-size source image in a development placement, not a newly approved optimized export. Distribution permission, responsive export provenance and final placement approval remain release inputs.

System fonts, dark surfaces, cyan accents and exact CSS colours are implementation proposals, not extracted website style facts. Quiet mode hides optional artwork and reduces colour decoration without removing identity, status or focus outlines. No animation is introduced. Forms have labels and counts, navigation has descriptive page names/current markers, status and errors use live regions, and native dialogs provide modal keyboard behaviour. Focus returns to the invoking control or an available recovery control. The conflict dialog initially focuses its heading so comparison instructions remain visible. The design reflows to a single column; no screen-reader or complete WCAG acceptance is inferred from these checks.
