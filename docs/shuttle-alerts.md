# Durable Shuttle Staff alerts

Scope: P06, P09, P14 and P16; partial T13–T16, T18 and T19. This adds automatic static notices for new help requests and Whitelist delivery problems. It uses the existing runtime, driver and core token boundary, with no dependency or licence change. Tests use only synthetic data and simulated Discord; production activation remains disabled.

## Routing and meaning

The development default posts in the member's already-bound private Shuttle case, mentioning only the mapped Staff role. This default was stated while requesting the owner's routing preference; it is not a claim that production IDs, role mentionability or live permissions have been approved. There is no arbitrary channel/URL destination, Head Admin case fallback, DM delivery, conversation excerpt, generated text or AI path. Existing Staff and lead ops channel access remains defined by the immutable case policy.

A new Ask Staff request commits its alert record and outbox intent with the request, optional pause, receipt and screen intent. Repeated clicks on an open request produce no second alert. Resolving help and asking again creates a distinct retained request and notice. Whitelist jobs record one delivery-problem alert per bound session when an attempted effect is uncertain, a job is parked, or its retry budget is exhausted. Reconciliation records uncertainty even after the original worker loses its lease. A failure notice suppressed before any possible send can be rearmed for a later problem at a new revision; obsolete job revisions cannot deliver it. Confirmed or possibly sent notices are never rearmed automatically. Alert failures cannot recursively create further alerts. Routine rate limits and temporary metadata-read failures do not create a new ping on each retry.

The messages report an event that was recorded and direct Staff to the current state. They do not claim that access was granted, that the problem is still present at the instant someone reads the message, or that a person has responded. An open help request may still need Staff after reading is complete. Alerts can reach Staff while the requester is Muzzled, without changing the pause, Muzzled, Crew or Whitelist. The existing rules still block progression and resumption.

## Delivery and uncertainty

The closed `shuttle.alert` job shares the existing per-member leases, fencing, Gateway continuity, durable delivery pause and backoff. Before sending, the core checks the retained source and current case binding, membership episode, case state and exact live channel audience. Closed cases, departed members, resolved help and recovered delivery failures suppress an unsent notice while retaining its record. Missing permissions or incompatible case policy park the job without changing permissions or redirecting it.

Screens and alerts share the private own-message proof implementation, with separate fixed validators, markers and interfaces. The alert adapter can only create or read one known static bot message. There is no edit, channel-history scan, arbitrary message fetch or user-text input. Preparation is single-use and rechecks current metadata. The payload permits precisely the configured Staff role; user, everyone and here mentions are disabled. Staff must be mentionable or the bot must already have the necessary channel permission. The implementation never grants that permission.

API contracts checked on 19 September 2026: Discord's [allowed-mentions rules](https://docs.discord.com/developers/resources/message#allowed-mentions-object) require both a visible mention and permission, and do not guarantee a push notification or human attention. The [message nonce](https://docs.discord.com/developers/resources/message#create-message) provides short-lived duplicate suppression only. The database remains the durable record of attempted and confirmed delivery.

Possible creation is committed before POST. A returned own-message ID is retained even from a late fenced worker; it is evidence for inspection, not authority to confirm. Confirmation requires a fresh read of that exact bot-owned message, its marker, static body and expected Staff mention, alongside current membership and channel checks. `confirmed` means the message was observed, never that Staff read it.

If POST loses its response and no ID was retained, the next inspection parks the attempt instead of sending another message. A known ID survives failed confirmation and permits read-only retry. Changed or missing messages remain unconfirmed and are not recreated automatically. A definite 429 or authorization refusal can release a still-unidentified attempt under its live lease; rate-limit backoff still applies. An in-flight POST may arrive after resolution or a policy change: its receipt remains retained, but the old worker cannot assert current delivery. No transaction makes Discord exactly once or retracts a notification already emitted.

## Schema, evidence and rollback

Migration `012-shuttle-alerts.sql` adds retained source identities, creation markers, message IDs and confirmation timestamps, plus the sixth closed outbox kind. Unique source keys bound duplicate help/failure notices. Earlier migrations remain unchanged. Historical help requests are not backfilled into a mass notification run; they remain in the Staff queue. Core keeps SELECT/INSERT/UPDATE only; the knowledge identity cannot read alert records.

Three contract tests cover the closed templates, mention/channel permissions, exact body and ownership proofs, single-use preparation, stale observations and forged proofs. L01–L21 cover transactions, coalescing, recovered/obsolete sources, role failures, lost responses, 429 backoff, fencing, missing mentions, closure/departure, delivery stops, attempt exhaustion, failed persistence, resolution during POST, database isolation, wrong case types, competing workers and Muzzled members. S17 restarts the isolated database, retains alert identities and confirms only the still-open request afterward. Existing screen and role suites exercise the shared adapter after extraction.

Rollback requires stopping commands and delivery, preserving migration 012, alert rows, messages, receipts and unfinished effects, and restoring code compatible with the alert job/state contract. Do not clear creation markers, recycle source IDs, replay uncertain POSTs, delete history or run a migrator that does not recognize the applied schema.

[Staff delivery-issue review](shuttle-delivery-issues.md) provides a private queue and audited rechecks. [Message recovery](shuttle-artifact-recovery.md) can identify an exact existing notice without sending another ping. Unidentified results, independent outage notification, full case lifecycle, production composition, live Discord mention/permission checks and visual acceptance remain open. A bot that cannot reach Discord cannot guarantee an alert through Discord; the independent outage/fallback requirement remains with the operations workplan. The owner's actual Shuttle copy stays unpublished.
