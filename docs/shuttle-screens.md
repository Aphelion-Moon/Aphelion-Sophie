## Publication and presentation

`publishOnboarding` checks current `shuttle.publish` authority and atomically records the immutable definition, 1–20 ordered steps, canonical SHA-256 and publisher grant metadata. An existing version cannot acquire different copy or reverse a withdrawal. The raw draft artifact is not a publication request. A metadata-only definition can still support internal domain fixtures, but cannot start the signed private experience without published copy.

Each stage has a bounded title and at most 5,000 characters of static copy. The renderer keeps the text in deterministic segments within one message, using at most six embeds and the platform's combined text limit. Only the final component row carries controls. There are no remote images, user-supplied message bodies, external fetches, model calls or automatic mentions. The owner's current draft fits these bounds, but wording, channel references, appearance and accessibility still require presentation/staging review.

The immutable publication accepts `helpPauses: false` or `true`. Ask Staff retains one open assistance request per session and displays its recorded status in the private case. False permits further progression; true disables progress controls and enforces a durable pause in the core. The [Staff assistance queue](shuttle-assistance.md) supports logged resolution, [eligible resumption](shuttle-pause.md) and later help requests with retained history. Neither rule claims that Staff has responded or received a notification. [Automatic Staff notices](shuttle-alerts.md) now have their own durable delivery records.

## Durable state and current controls

Entry, progress, help requests and confirmed Whitelist changes commit screen intents with their state. The outbox carries screen IDs and routing metadata, never compiled copy. Each message anchor retains its current session snapshot, access epoch and control revision. Page turns update that anchor and edit the same message. Replacement across runs/epochs queues retirement of the previous anchor. See [persistent pages and wording](onboarding-experience.md). Membership revocation retires controls in the same transaction; withdrawal and case closure queue cleanup with their state changes.

A signed component supplies an opaque screen ID, control revision and one allowed action. The core derives its member from the authenticated interaction, checks current self-service authority and membership, loads the stored private-case binding, and verifies fresh exact channel permissions. It then checks the original message ID, screen readiness, session version, stored nonce, definition and epochs. A component ID or visible channel never grants authority. Concurrent controls commit once; duplicate receipts cannot replace the screen of a newer repeat. Stale controls receive a fixed recovery response.

Acknowledgement on the final screen of the final step records acknowledgement and queues the existing Whitelist grant. The pending screen does not claim success. Completion is rendered only after the current role is observed and the existing grant checks succeed. Check completion requests a fresh final delivery attempt; mute, withdrawal or Whitelist loss still defeats old grants. Back never retracts a delivered role.

## Discord writes and recovery

`createShuttleMessages` is a core-only adapter for this bot's static Shuttle messages. It verifies bot identity, channel metadata, permissions, current membership observations and continuity before delivery. Fixed transport routes create, fetch or edit one known screen message; there is no channel-history scan or arbitrary-message export. Opaque observations bind the own-bot author, private channel, full screen marker and intended body. Reads discard unrelated response fields and never create an AI path.

`createShuttleDispatcher` performs at most one create/edit per call. The store commits possible creation before POST, and a successful HTTP response does not make controls ready: a fresh read must match the intended body and current policy. Discord's [message nonce option](https://docs.discord.com/developers/resources/message#create-message) adds short-lived duplicate suppression; it is not treated as durable exactly-once delivery. Component IDs use the documented [bounded button contract](https://docs.discord.com/developers/components/reference#button).

A lost create response with no retained message ID parks for review instead of issuing another POST. A subsequent explicit `/shuttle start` may retire that uncertain screen's authority and request a replacement. An unknown old message can remain visible because its ID was lost; its controls cannot match a ready current record. Known late results retain their IDs even when their worker or policy is obsolete, and queue current-state inspection. Inert replacement messages preserve the routing/history records. Failed or late edits are inspected and repaired, including after lease expiry.

If a known message was deleted, entry inspection records that observation, retires the old screen, and queues a fresh screen at the same stored progress. Repeated entry into an intact current screen merely inspects it. Paused delivery, bad copy hashes, changed audiences, unknown ownership and configuration errors do not authorize another write. There is still a race between final validation and Discord applying an in-flight request; post-response checks and reconciliation address it without claiming atomic external effects.
