# Retained case closure and reopening

This slice implements versioned Staff status, close and reopen operations for retained cases (P05/P06/P09–P11/P14/P16/P17; partial T04–T07/T09/T13–T16/T18–T22/T36/T59). [Ordinary ticket intake](case-intake.md) and [answer delivery](case-intake-delivery.md) are implemented separately. [Ordinary delivery recovery](case-delivery-issues.md) is also implemented. [Explicit participant changes](case-participants.md) share its case version and audience checks. [Initial Staff-contact intake](case-contacts.md) is implemented separately. Final forms, staff notes, attachment/transcript capture, archive placement, exceptional deletion, dashboard parity and production composition remain open. Staff assignment is documented separately in [case ownership](case-staff.md). There are no new dependencies, live credentials or AI paths.

## Approved closure audience

On 20 September 2026 the owner approved preserving read access for the existing requester, currently invited participants and the case type's configured responder roles while denying posting. Closure uses retained, authorized audience records; it does not import arbitrary Discord overwrites or grant permanent individual access to everyone currently holding a responder role. Role loss, invitation removal, departure and revocation still apply. Head Admin contact continues to exclude ordinary Staff; Staff Report includes Staff and lead ops. A reported subject is never added. Older closed/failed cases remain sealed under their existing policy until an explicitly authorised reopening. This policy decision does not certify live Discord permission behavior.

Closed overwrites deny Send Messages, Add Reactions, Embed Links, Attach Files, Create Public/Private Threads, Send Messages in Threads, Send Voice Messages, Send Polls and Use External Apps for humans, while preserving View Channel and Read Message History for the case audience. The bot retains its existing narrow message permissions for retiring its own controls. Permissions are verified as an exact set, and preparing a closed-mode write checks the bot holds the bits it will set. Discord's [permissions documentation](https://docs.discord.com/developers/topics/permissions) specifies separate thread posting permission and explains that denying Use External Apps limits responses from user-installed apps to ephemeral messages. It does not control server-installed apps. Guild owners/Administrators bypass overwrites; the bot cannot promise to prevent their changes or guarantee uninterrupted access policy during an in-flight request or outage. Existing child threads, other integrations and live Discord behavior still need staging verification.

## Shared use case and commands

`apps/core/storage/case-lifecycle.js` owns the versioned use case, with current `case.manage` authorization for the case's actual type and opener. `apps/core/discord/case-lifecycle.js` adapts the signed command envelope; `modules/tickets/lifecycle.js` provides bounded routing contracts, registration data and static metadata rendering. A future dashboard must call the same use case after authenticating its actor, rather than mutating storage directly.

| Command | Input and result |
|---|---|
| `/ticket status [case:ID]` | Current authorized case metadata, resource version and applicable command guidance. Omitting ID looks up the current channel's canonical case. |
| `/ticket close case:ID@VERSION reason:CODE` | Codes `resolved`, `duplicate`, `withdrawn`. Records closure intent and retires Shuttle controls atomically; reports pending closure until worker verification. |
| `/ticket reopen case:ID@VERSION reason:CODE` | Codes `follow-up`, `closed-in-error`. Requires current requester presence, responder authority and admission capacity/cooldown. Records a request; opening remains worker-confirmed. |

There is no free-text reason, arbitrary action, channel selection, case-content preview or generic retry option in these commands. A case reference is a concurrency token, never an access credential. Replies are ephemeral through the signed HTTP receiver and suppress all mentions. Status and mutation replies reauthorize before rendering. Registration data is available but no commands have been registered with Discord.

The [Staff case queue and ownership commands](case-staff.md) share this resource version. Status includes assignment diagnostics; a claim or reassignment never grants case access. A later ownership mutation cannot supersede pending lifecycle intent, but it does invalidate older version references.

## Durable requests and external effects

Migration 016 adds `closing`, `version` and `desired_access` to reservations, plus retained `case_lifecycle_actions`. An action contains its original version, signed interaction ID, reason code, requesting operator grant, request time and previous access intent. Its outcome is tracked separately as pending, confirmed, revoked, ineligible or superseded. It contains no case conversation, form, attachment or staff note.

The request, audit, interaction receipt, new case version, side-effect job and any Shuttle invalidation share one transaction. Current observations are checked again after lock/authorization waits. Duplicate signed requests retain one action, while stale versions and interaction collisions cannot overwrite a newer request. The version range reserves space for both a request and its later confirmation. Closing cases count against member capacity; new reopen requests share the admission budget and cooldown with new cases, while worker retries consume neither again.

The existing fixed `case.provision` worker applies current intent, verifies all retained noncanonical candidates remain sealed, then verifies the canonical channel and current requester membership. It does not create another channel for close/reopen. Reopening carries the current presence epoch and a recorded operator grant, checked again before and after the audience change. Lost authority or requester departure prevents confirmation and restores the earlier restrictive intent; a later return of Staff authority cannot revive that rejected action. A confirmed reopening becomes the established policy, rather than depending forever on the original operator's role. A subsequent explicit close can supersede a pending reopen, including without granting read access to a legacy sealed case.

Closing is a restrictive intent and continues if the requesting operator later loses authority. A departed requester causes sealing. The case remains `closing` until permissions are observed, and a failure retains the requested state for review. Unknown responses, expired leases and late writes retain separate reconciliation work; they never imply Discord exactly-once delivery. Gateway metadata changes schedule inspection of closed/failed cases and every registered candidate as well as open cases. [Periodic case inspections](case-inspections.md) now provide a bounded durable scheduling path; production wiring and review of blocked work remain required.

## Shuttle behavior

Closing immediately marks current Shuttle screens obsolete and queues edits to retire the bot's controls. A pending grant returns to active final-stage state with a fresh version/nonce, cancels ready/parked grant jobs and records compensation for possibly dispatched grants. A leased worker must recheck current state and cannot confirm the old grant. Reconciliation preserves already earned current Whitelist and removes an unsupported late grant. Reopening does not restore a retired control, clear a help pause, advance reading or issue a role: the member must request a current screen and explicitly acknowledge the final stage again. Muzzled, withdrawn definitions, Whitelist loss and departure epochs remain binding; actual Whitelist loss/departure requires a fresh Shuttle.

## Evidence, deployment and rollback

Six contract/adapter tests and J01–J17 exercise signed bounded commands, current permissions, private status, exact read-only audiences, optimistic versions, duplicate receipts, transaction rollback, head-admin restrictions, capacity, pause/mute, grant cancellation, compensation, both directions of late case writes, migration backfill and Gateway-triggered inspection. S24 restarts the isolated PostgreSQL cluster with pending closure, audit, retired controls and a delivery pause, then confirms using a recreated worker. Actual execution counts and source hashes belong to [verification](verification.md), not this specification. All case/role HTTP is simulated; the command receiver uses a real loopback socket with generated signing keys. No live permissions or real case data are used.

Core needs SELECT/INSERT/UPDATE on the new table; knowledge has no access and core has no DELETE. Applied migrations 001–015 are unchanged. Production IDs, capability mapping, command registration, service identities/ACLs and live recovery acceptance remain open. The closure audience is now approved. This does not establish off-host backups or completion of the full acceptance catalogue.

Rollback must stop delivery and preserve migration 016, reservation versions/access intent, every action/receipt/outbox row, channels, exclusions and revocation epochs. Restore compatible code after review; do not run the old unversioned `closeCase` implementation against this schema, drop history, delete channels or clear pending work to make old code run. No production service/schema was changed and no down migration is supplied.
