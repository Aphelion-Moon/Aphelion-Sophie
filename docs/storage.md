# PostgreSQL storage implementation

Scope: P01, P04, P06 and the storage portions of P10, P13–P16 and P19. PostgreSQL is approved as the infrastructure exception in ADR 0002. ADR 0003 records the MIT driver, its two named ISC indirect components and the limited use of existing Windows binaries for synthetic tests. Production provisioning is not part of this slice.

## Ownership and boundaries

`apps/core/storage/core-store.js` exposes specific use cases for membership observations, mute intents, Shuttle definitions/progress, case reservations and permanent channel exclusions. It receives a pool, clock and trusted authoriser. The authoriser must return `true` for a currently authorised operation; false, missing or thrown results deny it. The signed moderation command path now uses the real current-role authorizer and persistent capability epochs with synthetic Discord HTTP. Other tests retain explicit synthetic authorizers. Dashboard/OAuth routes must share these same use cases; see `docs/command-authorization.md`.

The only application import of `pg` is the explicit core pool factory. It requires a loopback address, explicit credentials and a Sophie-prefixed identity/database; it does not discover or reuse other services' PostgreSQL settings. The pool has four connections and bounded connection, statement and idle-transaction timeouts. External moderation handlers convert raw driver failures to stable outcomes. Storage exposes no SQL endpoint or token lookup; the separate loopback command adapter owns its own bounded HTTP interface. No AI worker is added.

The migration runner is a maintenance API for a separate privileged principal. The test core principal receives schema usage and SELECT/INSERT/UPDATE on core tables, with no DELETE, migration privileges or role creation. A separate synthetic knowledge principal is denied access to core tables. This tests PostgreSQL grants, not Windows account or filesystem isolation. Knowledge/inference must never receive this pool or core credentials.

## Transaction semantics

Every transaction uses a single checked-out connection. Rollback failure discards that connection. There is no automatic retry of an uncertain COMMIT; the caller retries the same interaction identity, and the persisted receipt resolves whether the operation committed.

Member operations lock a stable `(guild, member)` row. A current membership observation is stored first, advancing revocation epochs and retiring obsolete active sessions. A savepoint then protects the action: a rejected stale control does not roll back a valid observed revocation. A database/transport failure still rolls back the transaction and must leave delivery disabled until reconciliation.

The same transaction records a unique `(guild, interaction)` receipt, versioned progress and its intended outbox effects. A conflicting user or command cannot reuse that receipt. Receipts store outcome references, not authority snapshots; duplicate operations recheck access, eligibility epochs and definition withdrawal. Partial uniqueness allows only one current Shuttle per member, while previous sessions remain retained. Definitions are immutable by version; withdrawal cannot be reversed by republishing the same version. New visits select the latest published version; active visits stay pinned.

An observation, capability check and Discord request cannot be one atomic operation. The five-second development freshness contract remains a proposal to validate against staging. Persistent current capability epochs and role hierarchy checks are implemented. Migration 006 adds the [Gateway metadata journal](gateway-continuity.md): event cursor, observed revocations and inspection intents commit together, with fenced ownership and continuity stamps. Migration 007 adds a retained Identify budget. The socket supervisor has native WebSocket loopback coverage; [periodic case inspection](case-inspections.md) has offline coverage, while live composition and periodic member/role reconciliation remain open.

## Queue and confirmation

The outbox uses database time, row locks, `SKIP LOCKED`, renewable bounded leases and monotonically increasing per-job fencing tokens. A short database advisory lock serialises claims to enforce one live lease per member across effect kinds. No database transaction is held across Discord delivery. A lease is not permission to deliver: `inspectGrant` reloads current member, session and definition state first.

The grant check durably records that delivery may have started. A fresh role observation is needed to mark the Shuttle complete. After lease loss, the old worker cannot confirm; the next worker reconciles current state. If current policy rejects a possibly applied grant, cancellation and a `whitelist.reconcile` intent commit together. The Whitelist dispatcher now assesses current entitlement before compensation; it preserves a newer legitimate grant. See `docs/discord-delivery.md` for simulated HTTP evidence and the missing live observer/composition boundary.

Retries use bounded exponential backoff and honour a longer Discord Retry-After duration. Migration 002 adds a durable shared delivery cooldown/pause, which is rechecked before external mutations. After ten attempts a job is parked with its intent and dispatch marker retained; operator reconciliation is required. The code contains no general-purpose completion API that could acknowledge an arbitrary role job. Crew/Muzzled reconciliation has a concrete dispatcher with retained operator grants and fresh reauthorization. Private case provisioning now has its own dispatcher and opaque channel observations; see [case delivery](case-delivery.md). Database fencing does not make Discord exactly once and cannot recall an in-flight request.

Case admission locks the member and a guild budget row before counting/reserving capacity. Pending/open cases consume the member budget; pending provisioning consumes the guild budget. The receipt, reservation, immutable policy version, operation token and provisioning intent commit together. Every observed candidate is permanently excluded before audience access; exact fresh channel observations are required to confirm provisioning and release pending capacity. Closing a case preserves its metadata and exclusion. An uncertain/parked provisioning request continues to consume capacity until explicit reconciliation; a timeout alone is not proof that no channel was created. Migration 005 adds these records and a membership presence epoch, separate from Shuttle's Whitelist-loss epoch. Departure and later Gateway continuity-gap handling invalidate that presence epoch.

Migration 008 binds private Shuttle sessions to cases. Migration 009 adds approved static publications, screen snapshots/message IDs and retained assistance requests, plus the `shuttle.render` outbox kind. Progress, screen replacement and role confirmation queue presentation in the same transaction. [Screen delivery](shuttle-screens.md) independently checks current case permissions and message ownership; it cannot use a stored open flag as proof of access.

Resolution, receipt and current-screen refresh commit together. Current Staff authorization applies to queue reads and mutations; the queue is paged and metadata-only. Old, withdrawn or closed sessions are never reopened by resolving help.

## Running the synthetic checks on this host

Install the pinned driver using `npm ci --ignore-scripts --omit=optional`. `.npmrc` preserves those safeguards. Use `npm test` for pure/contract tests and `npm run test:storage` for real PostgreSQL integration. `node scripts/test-storage.mjs --record` records source hashes and successful results. These are separate from release acceptance.

The ignored `.local/postgres-runtime.json` identifies the existing binary directory, with no database credentials. The harness checks its executables, supporting DLLs and notice hashes against `legal/postgresql-test-runtime.json`; a changed build fails and needs review. On a different host, provide a reviewed matching binary directory before running it. Do not point it at a data directory or copy an existing service configuration.

Each run creates a new ACL-restricted `.local/postgres-tests/run-*` directory, initialises a new SCRAM-authenticated cluster, chooses a free loopback port and generates new passwords. It limits PostgreSQL to 16 connections and 16 MiB shared buffers. No Windows service or firewall rule is created. All database operations, including fault injection and stop/start, target that newly created cluster. The Windows launcher avoids inherited output pipes when starting PostgreSQL. The expanded conversation suite measured a 100.742-second shutdown checkpoint with 118,344 files synchronized after repeated synthetic TRUNCATE operations. Its first run failed the 90-second control deadline; the owned log/status confirmed eventual shutdown before retry. The harness now runs a bounded administrative CHECKPOINT between independent suites, never inside a stateful restart scenario. It still awaits pg_ctl asynchronously for up to 90 seconds inside a 95-second process deadline, with fsync unchanged. This permits progress reporting while the owned database flushes its checkpoint. It never restarts merely because an observation timed out. The harness closes its pools and stops the cluster in a `finally` block. Run directories contain only synthetic data and are retained locally for diagnosis, with a STOPPED marker; they are ignored by Git and are not backups.

## Migration, rollback and outstanding gates

Migration `001-core.sql` creates the core schema and migration ledger in a dedicated database. A transaction and fixed migration lock serialise competing runners; recorded SHA-256 checksums detect edits to an already applied migration. Use a new numbered migration for later schema changes. The original migration must not be edited after deployment.

No Sophie production schema exists to roll back. For this development slice, stop only a named test cluster owned by the harness and revert the application changes if required. Do not reverse or delete user plans, PNGs or existing game/wiki databases. Future production rollback must stop delivery, preserve the schema/state, verify compatible application and migration versions and reconcile unfinished jobs before restart. A destructive down migration is deliberately absent.

Release still requires a dedicated approved distribution/data root and service identities; live interaction registration, OAuth and trusted observation adapters; approved form copy and remaining case workflows; live ID/hierarchy/ACL checks; attachment acquisition/storage and authenticated transcripts; capacity/retention operations; independent recovery watermark verification; off-host backup destination and restore drill. An old database backup cannot establish the latest revocation ledger. No storage method or test result enables production mode; the production preflight still rejects activation.
