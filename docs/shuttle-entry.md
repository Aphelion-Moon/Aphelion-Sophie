# Signed Shuttle entry and private case binding

Scope: P06, P09, P10, P13, P14 and P16; partial T13–T16, T19, T53–T55 and T59 evidence. This slice connects authenticated self-service entry to durable session and private case creation. [Published screens and controls](shuttle-screens.md) now supply the subsequent stage-delivery path. The draft guidance remains unpublished. No dependency, licence exception, production credential or service change was added.

## Entry and ownership

`modules/onboarding/entry-controls.js` supplies a persistent Board the Shuttle button and the `/shuttle start` command definition as data. They are not registered or posted automatically. The interaction verifier accepts only those exact entry shapes alongside the existing moderation commands. It verifies the original signed bytes, application, guild installation and member identity, then discards incoming messages, role arrays and resolved objects. A component ID routes the request; it grants no authority.

`createShuttleCommands` derives the target from the verified member, obtains fresh Discord metadata, and invokes the shared `openShuttle` store method. The store independently checks current self-service authority, guild presence, Muzzled status and durable mute intent. No caller can specify a different member, session, case or workflow version through the Discord entry controls. The HTTP receiver acknowledges privately before the database operation. With the navigation adapter injected, its reply distinguishes a pending reservation from a currently verified private destination; neither state claims Whitelist was granted.

## Atomic start and resume

The member lock serializes competing entry requests. One transaction commits the current session, private Shuttle case reservation, owner binding, interaction receipt and provisioning intent. Member and guild quotas use the same locked budget as ordinary cases. A failed quota check or binding insert leaves none of that request's partial state behind. Observed revocations remain durable when a domain action is rejected, using the existing member-operation contract.

An eligible active session resumes its pinned, still-published definition and immutable copy. Repeated interaction receipts cannot restart progress, restore access or replace a newer repeat's screen. A new run selects the latest published version and starts at page one. Whitelist loss invalidates the previous run; departure also changes the membership episode. Both require a fresh run. Muzzled members cannot enter or resume until eligible again.

A repeat in the same membership episode may reuse its still-open private Shuttle case under the same immutable audience policy. Separate session rows retain each run's history without consuming another open-case quota. A departed member's old case cannot be reused after rejoining. A closed case or withdrawn pinned definition fails closed and retains its records for operator attention; the entry operation never reopens it automatically.

Reusing a case schedules current-policy inspection unless a pending inspection already exists. The stored `open` flag is not proof of current Discord permissions and does not authorize sending page content. The screen dispatcher separately verifies the current channel, audience, membership, session version and epochs before delivery.

## Returning to the private case

`createShuttleNavigation` resolves the verified member again when preparing the ephemeral entry response. The store locates the session behind that member's current screen, including a valid completed screen, and checks current self-service authority, membership, eligibility epoch, published copy, private case ownership, presence epoch and audience-policy version. It does not select a historical session from an interaction receipt or order arbitrary session IDs to guess the latest run.

A pending case returns a static Open Shuttle button using the existing signed entry route. The member can check again after provisioning; the response does not invent a channel link, wait on a background timer or retain the interaction token in a queue. An open case requires a fresh opaque channel observation and exact expected permissions. A second transaction repeats member/session/policy checks and confirms that the observed channel still belongs to that current destination. Changed permissions, a moved/deleted channel, withdrawal, closure or an invalid membership episode suppress the link. No messages, forms or transcript data are read.

The renderer accepts only bounded guild/channel IDs and builds an Open Shuttle link to Discord's fixed channel path. It accepts no caller-supplied URL. The responder checks its delivery gate and the verified interaction's token lifetime again after lookup, suppresses all mentions and clears obsolete buttons on status-only replies. The ready message describes channel availability, not delivery of every page or completion. Following the link does not itself confer channel or role access; Discord and each subsequent Shuttle operation still enforce their own current checks.

This uses the existing legacy Action Row/Button presentation: a pending button has a custom ID, whereas the ready link has a URL and creates no bot interaction when followed. The fixed responder edits only the original ephemeral response. API references checked on 19 September 2026: [Discord button structure](https://docs.discord.com/developers/components/reference#button), [legacy component behavior](https://docs.discord.com/developers/components/reference#legacy-message-component-behavior), and [editing an interaction response](https://docs.discord.com/developers/interactions/receiving-and-responding#edit-original-interaction-response). Live behavior remains unverified.

Navigation adds no migration or dependency. Production composition must explicitly inject this adapter; the older static-status responder remains available for independent moderation tests.

Migration `008-shuttle-case-binding.sql` adds a retained binding table and composite ownership constraints. It does not invent bindings for legacy synthetic sessions. Such an unbound session fails closed at the new entry path and needs an explicit migration/recovery decision before production. Core retains SELECT/INSERT/UPDATE only; no deletion or knowledge-identity access is added. Earlier migrations are unchanged.

Rollback: stop entry and delivery, retain sessions, bindings, receipts, exclusions and outbox state, and restore compatible application code. Do not remove an applied migration, replay an old completion, reopen closed cases or publish a draft as a rollback shortcut. All tested clusters and listeners were stopped; production activation remains disabled.
