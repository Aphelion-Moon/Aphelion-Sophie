# Recovery of uncertain Shuttle cases and messages

Scope: P06, P09, P10, P14, P16 and P17; partial T04, T05, T13–T16, T19, T36 and T59. This extends the [Staff delivery queue](shuttle-delivery-issues.md) to private-case provisioning, static Shuttle screens and Staff notices. No dependency, licence, token ownership or production activation change is introduced.

## Staff workflow

`/shuttle issues` includes only retained, parked deliveries that resolve through an actual bound Shuttle session and case. Current Staff or lead ops authority is required for reading the queue, inspecting a recovery reference, committing the action and returning queue metadata. Head Admin contact and other case types are excluded. The queue contains bounded references and static status guidance, never conversation excerpts, forms, attachments or notes.

Recheck makes the original operation available to its existing worker. For a case whose creation may have succeeded, the worker searches current channel metadata for the original operation marker. A single matching candidate can be retained and inspected under current membership and case policy. If the member has departed, the candidate is sealed instead of restoring access. If no candidate exists, the case stays parked and still consumes its reservation quota; no second create is inferred safe. Multiple candidates remain retained and excluded, and ambiguity still requires deliberate operator review. The separate [channel-selection workflow](shuttle-channel-selection.md) records an explicit choice and verifies every other candidate as sealed; no duplicate evidence is discarded.

For a screen or alert whose POST may have succeeded without returning an ID, Recheck is disabled and the queue provides a versioned recovery reference. Staff identify the matching Sophie message in that private case, copy its Discord message ID, and invoke `/shuttle recover issue:<reference> message:<message ID>`. Both inputs have closed formats. There is no message-history search, URL input, arbitrary channel selector, SQL, bulk replay or new message-body input. Case selection and role grants cannot be performed through this command.

The core reads that one ID from the bound case and verifies the bot author, original record marker, attachment-free static format, exact expected body, fresh continuity and private channel audience. Alerts must also contain exactly the expected Staff mention evidence. Screen recovery accepts only the original static screen or its approved inert form. A copied marker, another author, changed body, wrong case, missing message or forged/expired observation cannot be adopted. Unrelated message content is never returned by the command or stored as recovery evidence. No case data reaches AI.

API contracts checked on 19 September 2026: Discord's [message structure](https://docs.discord.com/developers/resources/message#message-object) makes `components` optional. An absent field is treated as an empty list and still compared with the exact template; malformed values remain invalid. The [single-message read](https://docs.discord.com/developers/resources/message#get-channel-message) requires View Channel and Read Message History. The [command option schema](https://docs.discord.com/developers/interactions/application-commands#application-command-object-application-command-option-type) defines the bounded input fields as STRING options. Documentation checks do not replace live compatibility tests.

## What recovery records

The transaction records the message ID, operator grant, signed interaction ID, expected issue revision, old fence and error/attempt evidence together with the requeue and receipt. It preserves `create_started`, `dispatch_started`, the original effect and all history. It does not mark the screen ready, confirm a notice, change session progress, resume help or grant a role. Duplicate signed requests retain one outcome; competing or stale revisions cannot replace the result.

The worker then obtains fresh observations. An eligible current screen may become ready only after ordinary verification. A recovered older or Muzzled screen is made inert without replacing a newer screen. A resolved or otherwise obsolete alert remains historical without another ping. Known changed/missing notices remain unconfirmed; Recheck does not repost them. An action that was definitely never attempted may make its first send after the underlying problem is fixed. Global pauses, cooldowns, live leases and Gateway continuity still apply.

Recovery descriptions use read-only binding queries without session/case row locks. Mutation still locks the member, job, issue and state, then rechecks current authority and proofs. An operator selection never substitutes for these checks. A late result can still arrive after a timeout or permission change; retained evidence and worker reconciliation handle that uncertainty rather than claiming exactly-once Discord delivery.

## Migration, evidence and rollback

Migration `014-shuttle-artifact-recovery.sql` extends the existing action audit with `recheck` versus `adopt_message` and a bounded result ID. Earlier audits default to `recheck`. It backfills only parked, owned Shuttle artifact jobs without replaying them. A case reused across repeat visits retains its existing issue binding. Existing numbered migrations remain unchanged, and the knowledge identity has no access to this schema.

Contract checks cover the versioned slash inputs, closed routes and recovery guidance. F01–F19 cover late/absent/departed cases; lost screen and alert responses; false authors, markers, bodies, attachments and mentions; duplicate/colliding requests; authority/proof/ACL failure; historical and Muzzled recovery; newer screens; known changed notices; transaction rollback; case-type isolation; an unattempted notice; migration backfill and nonblocking metadata descriptions. S22 restarts the isolated database after message identification but before confirmation, retaining the audit, duplicate receipt, possible-create marker and delivery pause, then confirming through a new message verifier without another POST. Executed results and exact source hashes are recorded in [verification](verification.md).

Rollback requires stopping commands and workers, retaining migration 014, message IDs, audits, issues, receipts and unfinished effects, and restoring compatible code. Never clear possible-create markers, delete candidates, downgrade to an incompatible migrator or replay unknown POSTs.

Live Discord rendering, permissions and API compatibility remain untested. Unknown-message resolution when Staff cannot identify a result, ordinary ticket workflows, reconciliation service wiring, dashboard parity, production composition and independent recovery remain open. The owner's actual Shuttle copy remains unpublished. Only isolated synthetic databases and loopback listeners were exercised; no production service or Discord state was changed.
